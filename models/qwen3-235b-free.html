What Is Qwen3 235B A22B?

Qwen3 235B A22B is Alibaba's flagship open-weight language model, released on April 28, 2025 as the crown jewel of the Qwen3 model family. The name is precise: 235B refers to 235 billion total parameters, and A22B refers to 22 billion active parameters per forward pass — the key to understanding why this model is both powerful and cost-accessible.

It is a Mixture-of-Experts (MoE) architecture, meaning the 235 billion parameters are organized into specialized expert sub-networks. Only a subset of those experts activates for any given input, and in Qwen3 235B that active subset adds up to roughly 22 billion parameters — about 9% of the total. The rest of the parameter space sits dormant for that token, waiting to be routed for inputs that match their specialization.

The result is a model with the representational depth of 235 billion parameters, but the inference cost profile of a much smaller 22 billion parameter dense model. At launch in April 2025, Qwen3 235B A22B was competitive with or better than frontier models costing $10–20 per million output tokens, at a fraction of the price.

Architecture

235B total parameters, Mixture-of-Experts design. 22B active per forward pass. Approximately 9% parameter utilization per token — delivering dense-model expressiveness at sparse-model compute cost.

Context Window

32K tokens natively, extended to 131,072 tokens via YaRN-based positional scaling. Long-context performance degrades gracefully across the full range.

Multilingual

100+ languages and dialects. Strong on major European languages, Chinese, Japanese, Korean, Arabic, and regional Asian languages — not just English-dominant performance.

Capabilities

Math, coding, logical reasoning, instruction following, agent tool-calling, and multilingual tasks. Knowledge cutoff: March 31, 2025. Open-weight: self-hostable.

The Free Tier: What It Was

The :free variant of OpenRouter models provides access to the same underlying model weights at $0.00, with operational constraints instead of pricing gates. For qwen/qwen3-235b-a22b:free, that meant accessing the full Qwen3 235B A22B model — 235 billion parameters, dual-mode reasoning, 131K context — without paying a single cent per token.

The trade-offs of the free tier versus the paid tier were operational, not qualitative:

  • — Lower rate limits: Fewer requests per minute and a daily token cap. Fine for development and low-volume workloads; a constraint for high-throughput production.
  • — Higher latency: Free-tier traffic was routed lower-priority than paid traffic on shared provider infrastructure. Expect longer time-to-first-token, especially during peak hours.
  • — No SLA: No contractual uptime guarantees. Service could be degraded or unavailable without notice. Not suitable for customer-facing production deployments.
  • — Model quality: identical. The weights are the same. The same 235 billion parameters, the same MoE routing, the same thinking mode — just served differently.

For researchers, independent developers, and small teams, the free tier was the most accessible point of entry to a genuinely flagship-class model. The rate limits that constrain high-throughput production use cases are invisible for exploratory or low-volume work.

MoE Architecture Explained

Mixture-of-Experts is the architectural innovation that makes Qwen3 235B both powerful and cost-accessible. In a conventional dense language model, every parameter participates in processing every token. A 235B dense model would require activating all 235 billion parameters for each forward pass — expensive to serve and slow to run.

MoE models work differently. The parameters are divided into "expert" sub-networks, and a learned routing mechanism decides which experts to activate for each token. In Qwen3 235B A22B, only approximately 22 billion parameters are active per forward pass — about 9% of the total. The remaining 213 billion are dormant for that token, not consuming compute.

A useful analogy: Think of a massive reference library where each book is an expert sub-network. A dense model reads every book for every question. A MoE model uses a smart routing system to identify the most relevant shelf and reads only those books — faster, cheaper, and in practice often just as thorough, because the right books are the ones that matter.

The practical consequence for pricing is significant. Inference cost scales primarily with active parameters, not total parameter count. A 235B MoE model with 22B active parameters has a cost profile much closer to a 22B dense model than to a 235B dense model. This is why qwen/qwen3-235b-a22b can be priced at $0.455/$1.82 per million tokens while delivering capabilities that compete with models at 10–20× the cost.

The model stores the knowledge and representational capacity of 235 billion parameters but only burns the compute of approximately 22 billion per token. You are accessing 235B of distilled knowledge through a 22B compute window — and paying only for the compute.

Thinking vs Non-Thinking Mode

One of Qwen3 235B A22B's most distinctive features is its dual-mode reasoning design. Unlike models where either all responses are fast or all responses are deliberative, Qwen3 235B lets callers choose on a per-request basis.

Thinking Mode

The model generates a structured internal reasoning chain before producing the visible response. This chain — visible as reasoning tokens in the API response — covers assumption analysis, constraint checking, alternative exploration, and self-correction.

Best for: Complex multi-step reasoning, math problems, code architecture, research synthesis, any task where deliberation improves accuracy.

Reasoning tokens count toward output billing. At $1.82/1M, extensive thinking adds cost — but often improves result quality substantially for hard tasks.

Non-Thinking Mode

The model responds directly without generating a reasoning chain. Faster time-to-first-token, lower total token count, and cheaper per exchange when the task doesn't benefit from extended deliberation.

Best for: Conversational responses, simple Q&A, classification tasks, summarization, and any request where the answer is straightforward enough that reasoning overhead adds no value.

Same model weights, same knowledge — just without the scratchpad. Ideal for high-throughput use cases where cost-per-exchange matters more than analytical depth.

This flexibility is what makes Qwen3 235B uniquely versatile. It can serve as a high-depth reasoning model when you need it — think o1-class deliberation — and as a fast chat model when you don't, all within the same API endpoint and the same model ID. The free tier would have supported both modes.

Current Status: "No Endpoints Found"

As of the time of writing, querying qwen/qwen3-235b-a22b:free via the OpenRouter API returns the following error response:

OpenRouter API Error Response {
  "error": {
    "message": "No endpoints found for qwen/qwen3-235b-a22b:free.",
    "code": 404
  }
}

This 404 error is OpenRouter's way of saying that no provider is currently routing this model ID at the free tier. On OpenRouter, model availability depends on providers — inference infrastructure operators who agree to serve requests for a given model. The :free suffix indicates that the provider absorbs the cost; when no provider is willing to do so for a given model, the free tier returns "no endpoints."

This can theoretically be temporary — if a provider were to re-add the model to their free-tier routing, the model ID would come back online. In practice, free tiers for flagship 235B models are expensive to maintain and tend to be retired permanently rather than intermittently unavailable. The economics of serving a 235B MoE for free at scale are challenging, and Alibaba and OpenRouter providers have apparently concluded that the paid tier is the appropriate access point going forward.

What "no endpoints" means in practice: It is not a rate limit error, not a temporary outage, and not a geographic restriction. The model ID qwen/qwen3-235b-a22b:free is simply not routed anywhere. Any application using this model ID as a string constant will fail with a 404 until and unless a provider re-adds it — which is unlikely for this model.

What is OpenAI o3?

OpenAI o3 is the third generation of OpenAI's o-series reasoning lineup — models built from the ground up to deliberate before responding rather than generating answers in a single forward pass. Where GPT-4o and similar models produce output token by token immediately, o3 runs an extended internal chain-of-thought process invisible to the caller, working through the problem before committing to a final response. This architecture shift unlocks qualitatively better performance on tasks where the answer requires multi-step derivation: competition-level mathematics, formal proofs, complex code correctness, and scientific hypothesis evaluation. Tasks that would trip up a fast generative model — because getting to the right answer requires backtracking, checking intermediate steps, or holding many constraints simultaneously — are exactly the class of problems o3 was designed to handle.

The internal reasoning mechanism has a direct effect on pricing that developers need to account for. When o3 processes a request via OpenRouter, the API returns a reasoning_tokens field in the usage response — in a typical benchmark exchange, 320 of 700 completion tokens were reasoning tokens. Crucially, those reasoning tokens are encrypted: they never appear in the visible output text, but they do consume output token budget and are billed at the output rate. This means the actual cost of running o3 on genuinely hard problems — where the model thinks longer — will exceed what a simple token-count estimate suggests. For tasks where correctness matters above all else, this is the right tradeoff; for high-volume simpler tasks, o4-mini or a non-reasoning model will be more cost-efficient.

What o3 Excels At

o3 delivers its best results on hard, structured problems where extended deliberation produces meaningfully better answers than speed.

Advanced Mathematics

Competition-level problems, formal proofs, and multi-stage algebraic reasoning. o3's internal chain-of-thought allows it to check intermediate steps and backtrack when a derivation goes wrong — a capability that direct-generation models lack on complex proofs.

Scientific Analysis

Hypothesis evaluation, research synthesis, and complex data interpretation across physics, chemistry, and biology. o3 can hold multiple competing hypotheses in working context and reason about which evidence best distinguishes them.

Hard Coding Problems

Algorithm design, debugging subtle logic errors, and system architecture decisions. o3 reasons through correctness constraints before writing code, catching edge-case failures that surface only on adversarial inputs or at boundary conditions.

Multi-Step Planning

Strategic planning with constraints, decision trees, and optimization problems. Tasks where the solution path through a dependency graph matters as much as the final answer — scheduling, resource allocation, and risk modeling.

What is a Context Window?

A context window is the maximum number of tokens the model is allowed to "see" at once: prompt tokens + system messages + user messages + the model's own generated tokens so far ≤ window_size. Anything outside the window is invisible to the model — it has no weights pointing to those tokens.

Why Window Size Matters

Working memory for reasoning: Multi-step tasks (code analysis, chain-of-thought, multi-turn dialogue, long JSON editing) need earlier steps to remain inside the window. If intermediate reasoning scrolls out, hallucinations spike as the model loses its reasoning thread.

GPU/RAM usage and latency: Standard dense attention is O(n²) in tokens. Even with FlashAttention2 reducing the constant, the KV-cache grows linearly with sequence length. 128K tokens already demands tens of GB of GPU VRAM per request; 1M tokens requires sharded multi-GPU inference or specialized linear-attention variants — which is why 1M context costs more and responds slower.

Model quality: Most frontier LLMs are specifically tuned for 8K–128K. Beyond that, perplexity grows and "lost in the middle" effects appear unless the vendor has done dedicated long-context training. A 1M window does not guarantee perfect recall across the full span.

Token Pricing at Scale

Input and output are priced separately — output usually costs 3–5× more per token. At volume, naively filling a large context window per call can easily 10× your inference bill compared to targeted retrieval. The smart pattern: use RAG to keep context under 32K for most requests, reserving the full window only for tasks where holistic access genuinely improves output quality.

128K vs. 1M for Production

Default to 128K: covers most enterprise use cases (contract review, codebase Q&A, long conversations). Move to 1M only when you have verified tasks requiring it — full repository analysis, book-length synthesis, or legal document comparison spanning hundreds of pages. Measure actual context utilization before paying the 1M premium; most apps average well under 32K per call.

Key Takeaways

  • o3's $0.003700 benchmark cost is competitive — pricing dropped dramatically from earlier estimates, putting it within range for production reasoning workloads.
  • Internal reasoning tokens (not visible, but billed) mean actual complex-task costs run higher than the benchmark suggests — budget accordingly for hard problems.
  • The 200K context window handles full codebases and research papers alongside the reasoning task without needing to chunk input.
  • Use o3 for tasks where answer correctness matters more than speed — it's not a conversational model and shouldn't be priced or deployed like one.

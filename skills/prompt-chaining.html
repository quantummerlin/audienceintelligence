Prompt Chaining:
The Framework That Makes Complex AI Tasks Actually Work

Most AI prompts fail not because the model is incapable, but because they ask it to do too much at once. Prompt chaining solves this by splitting work into focused stages — each output feeding the next. Here's why it works, and exactly how to build your own chains.

Why Single-Shot Prompting Fails

You've experienced this before: you write a carefully crafted prompt asking an AI to research a topic, analyse it, draw conclusions, and write a polished summary — all in one go. The result is either too shallow, confidently wrong, or weirdly truncated. You try again with a longer, more detailed prompt. Still not right. You add more instructions. Still disappointing.

The problem isn't your writing. It's the architecture.

When you ask a language model to do multiple cognitively distinct tasks in a single prompt, you're asking it to hold too many competing objectives at once. Extraction, verification, synthesis, and formatting all require different "modes" of reasoning. Bundled together, the model makes trade-offs you didn't intend — cutting depth to hit format requirements, skipping verification because the extraction already filled the context, or doing surface-level synthesis because there was no dedicated step for anything else.

⚠
The hallucination trap

Single-shot prompts are most dangerous when they mix research and synthesis. The model will generate a confident, well-structured answer that blends real facts with plausible-sounding inventions — because it's optimising for a coherent output, not a verified one.

Research on this is consistent: complex reasoning tasks produce significantly better results when broken into steps. Anthropic's own work on chain-of-thought prompting showed that explicit reasoning steps reduce errors on multi-step problems. The same logic applies at the task architecture level — if you want better outputs, you need to engineer the workflow, not just the wording.

The three ways single-shot fails

  • Shallow depth: The model needs to hit every requirement you listed, so it gives each one the minimum viable treatment rather than doing any of them properly.
  • Unverified claims: With no dedicated verification step, the model blends retrieved facts and confident confabulation. There's no internal mechanism to flag the difference.
  • Format-content conflict: When you specify both the analysis required and the output format, the model will sacrifice analysis quality to fit the format rather than let the format be shaped by the content.

What Is Prompt Chaining?

Prompt chaining is the practice of breaking a complex task into a sequence of smaller, focused prompts — where the output of each step becomes the input for the next.

Instead of one prompt that asks for research + analysis + verification + a polished write-up, you create four separate prompts. Each one has a single job. The model can do that single job well, produce structured output, and pass it cleanly to the next stage.

The result is a pipeline: inputs flow in, a series of focused transformations are applied, and a high-quality output comes out. The pipeline is auditable (you can inspect any stage), recoverable (if one stage fails, you fix that stage and re-run from there), and improvable (you can swap in a better model or prompt for any individual step without rebuilding everything).

✓
The key insight

Prompt chaining doesn't make the model smarter — it makes the system smarter. You're providing the architecture that the model's individual capabilities can actually shine within.

Single-shot vs. chained: a direct comparison

Dimension Single-Shot Chained
Output depth Shallow — spread across requirements Deep — each step fully focused
Hallucination risk High — no verification mechanism Lower — explicit verify step
Debuggability Opaque — hard to see where it went wrong Transparent — inspect any stage
Cost Lower — one call Higher — multiple calls
Speed Faster for simple tasks Slower — sequential calls
Consistency Variable — slight wording changes shift results More consistent — structured at each step

The cost and speed trade-offs are real — but for complex tasks, they're worth it. A single-shot prompt that produces an unusable result and requires 10 retries is slower and more expensive than a three-step chain that works the first time.

The Core Mechanics

There are three things that make a prompt chain actually work: output formatting, clean handoffs, and role assignment. Get these right and chains are remarkably reliable. Skip any of them and you'll spend hours debugging.

1. Output formatting

Every step in a chain must produce output in a format the next step can reliably consume. The most common mistake is letting a step produce unstructured prose and then feeding it into a step that expects to work from specific data points. You end up with the second step summarising the first step's prose rather than doing its actual job.

Use JSON for machine-processed data, numbered or bulleted lists for items that need to be iterated over, and clearly labelled sections for complex outputs that combine multiple types. Always specify the output format explicitly in the prompt — never assume the model will infer it.

Bad — unformatted output 
Extract the key claims from the following article.

[article text]
Good — structured output specified 
Extract every factual claim from the article below.
Output ONLY as a JSON array — no preamble, no commentary.
Schema: [{ "claim": "...", "source_sentence": "..." }]

ARTICLE:
[article text]

2. Clean handoffs

Each step should receive exactly what it needs and nothing more. Don't feed a 3,000-word article into a verification step when all it needs is the 12 claims extracted in step 1. Trim the input to the relevant data at each handoff. This improves accuracy (the model focuses on the right thing) and reduces cost (fewer tokens processed).

Use a simple template for all handoffs: inject the prior step's output into a clearly labelled block, and tell the model explicitly what that block is.

3. Role assignment

Assign a different, focused role to each step. "You are a research assistant" gives the model a very different orientation than "You are a fact-checker" — even when asked to look at the same content. Role assignment isn't just flavour text; it primes the model's reasoning mode for the type of task that step requires.

◆
Temperature tip

Set temperature to 0 for extraction and verification steps — you want deterministic, predictable output. Use 0.7–1.0 for synthesis and writing steps, where creative variation improves output quality.

Step-by-Step Walkthrough

Let's build a real chain from scratch. The task: produce a research brief on any given topic. We'll take raw input — an article, a transcript, or a collection of notes — and produce a polished, verified, executive-ready brief.

Step 1 of 4

Extract — pull out every factual claim

The model's only job here is extraction. No analysis, no summary. Just identify every discrete factual claim and output them as a structured list. Use temperature 0.

Step 1 Prompt — Extract 
ROLE: You are a precise research assistant.

TASK: Extract every factual claim from the text below.
A "factual claim" is any assertion about the world that could be verified.
Do not include opinions, predictions, or vague statements.

OUTPUT FORMAT: JSON array only. No preamble, no explanation.
Schema: [{ "id": 1, "claim": "...", "quote": "..." }]
Where "quote" is the exact sentence from the source.

SOURCE TEXT:
[PASTE YOUR SOURCE CONTENT HERE]
Step 2 of 4

Verify — score confidence and flag gaps

Feed the JSON array from step 1 directly into this prompt. The model rates each claim's confidence (based on its training knowledge) and flags anything that needs external sourcing. Use temperature 0.

Step 2 Prompt — Verify 
ROLE: You are a rigorous fact-checker.

TASK: For each claim in the JSON below, assess its reliability.
Rate confidence 1–10 (10 = certain, 1 = likely false).
Flag any claim that requires an external source to verify.

OUTPUT FORMAT: Return the same JSON array with added fields.
Schema: [{ "id": 1, "claim": "...", "confidence": 8, "needs_source": false, "note": "..." }]
The "note" field is mandatory — explain your confidence rating briefly.

CLAIMS TO VERIFY:
[PASTE STEP 1 JSON OUTPUT HERE]
Step 3 of 4

Filter — keep only high-confidence claims

This is often just a code step (filter the JSON for confidence >= 7 and needs_source === false), but you can also do it with a prompt. Either way, you end up with a clean, verified claim set to build from.

Step 3 — Filter (code or prompt) 
# Option A: Python (fastest)
verified = [c for c in claims if c["confidence"] >= 7 and not c["needs_source"]]

# Option B: Prompt
From the claims below, return only those where confidence >= 7
and needs_source is false.
Keep the same JSON schema.

CLAIMS: [PASTE STEP 2 OUTPUT]
Step 4 of 4

Synthesise — write the brief using only verified data

Now the model writes. Crucially, it's working only from a clean, verified set of claims — not from the original messy source. The constraints produce better writing. Use temperature 0.7.

Step 4 Prompt — Synthesise 
ROLE: You are a senior analyst writing for an executive audience.

TASK: Write a 3-paragraph research brief using ONLY the verified claims below.
Structure: Context → Key Findings → Implications.
Cite each claim inline as [claim_id].
Do not introduce any information not present in the claims.
If the claims are insufficient for any section, note that explicitly.

FORMAT:
Context (1 paragraph): Background and why this matters.
Key Findings (1 paragraph): The most important verified facts.
Implications (1 paragraph): What this means for decision-makers.

VERIFIED CLAIMS:
[PASTE STEP 3 OUTPUT HERE]

The output of step 4 is a well-structured brief built entirely from verified, attributed claims. No hallucinations. Fully auditable. You can trace every sentence back to a source claim, and every claim back to the original quote.

The Five Chain Patterns

Most prompt chains are variations of five core patterns. Learn these and you can construct a chain for almost any complex task.

Linear

A → B → C. Each step feeds the next. The most common pattern. Use for: research briefs, structured analysis, any multi-stage transformation.

Branching

A → B and C (parallel). Run two independent analyses on the same input, then merge the results. Use for: comparing approaches, multi-perspective analysis.

Looping

A → B → [check] → A. Re-run a step if output doesn't meet a quality threshold. Use for: generation tasks where you need to hit a specific standard.

Fan-out / Fan-in

A → [B1, B2, B3] → C. Process multiple items in parallel, then aggregate. Use for: analysing multiple sources, batch processing.

Self-critique

A → [critique A] → [revise A]. The model generates output, then critiques it, then revises. Use for: high-stakes writing and reasoning tasks.

The self-critique pattern in detail

This pattern is especially powerful for writing and analysis. You run three prompts: generate, critique, revise. The result is consistently better than asking the model to generate a great response in one shot — because "revise this based on these specific flaws" is a much more tractable task than "write something excellent."

Self-Critique Chain 
--- PROMPT 1: Generate ---
Write a [content type] about [topic].
[Your content requirements here]

--- PROMPT 2: Critique ---
You are a critical editor reviewing the draft below.
Identify the 3 most significant weaknesses:
1. Arguments that are weak or unsupported
2. Clarity problems
3. Structural issues or missing sections
Be specific. Quote the problematic sections.

DRAFT: [STEP 1 OUTPUT]

--- PROMPT 3: Revise ---
Rewrite the draft below, addressing every critique listed.
Do not introduce new ideas — only fix the identified problems.

DRAFT: [STEP 1 OUTPUT]
CRITIQUE: [STEP 2 OUTPUT]

Handling Errors and Edge Cases

Every chain will eventually encounter a step that produces unexpected output. A verification step returns malformed JSON. An extraction step misses half the claims. A synthesis step ignores its instructions and goes off-script. Here's how to handle each.

Malformed JSON

The most common failure in structured output chains. Fix it with three defences:

  • Ask twice: End your extraction prompt with "Double-check your JSON output is valid before responding." Sounds trivial — it meaningfully reduces malformed output.
  • Specify what's not allowed: "Do not include trailing commas. Do not wrap the JSON in markdown code blocks." These specific prohibitions catch the most common malformation patterns.
  • Repair as a step: If you regularly get malformed JSON, add a lightweight repair step using a cheap model: "Fix any syntax errors in the JSON below. Return only the corrected JSON."

Incomplete extraction

The model extracted 8 claims but you can see there are clearly 15 in the source. Add this to your extraction prompt: "Before finalising your output, re-read the source and verify you have not missed any factual claims. If you find additional claims, add them." A second-pass instruction at the end of the prompt improves recall significantly.

Step ignoring instructions

A synthesis step that starts inventing information not in the claims list, or a verification step that just agrees with every claim. This is usually a sign your prompt is too long and the instructions at the top are being underweighted. Move your most critical constraints to the bottom of the prompt — models weight recent tokens more heavily. The instruction "DO NOT add any information not present in the verified claims below" should be the last line before the data, not the first.

◆
Log every step

When building a new chain, log the full output of every step to a file before passing it to the next. You'll spend far less time debugging if you can see exactly what each step received and produced.

Common Mistakes (and How to Avoid Them)

Mistake 1: Too many steps

More steps is not always better. A 10-step chain introduces 10 potential failure points and multiplies your cost. Start with the minimum viable chain — usually 3–4 steps. Add a step only when you can identify a specific failure mode it would prevent.

Mistake 2: Not specifying output format

Already covered in mechanics, but worth repeating: this is the most common mistake and the source of most chain failures. Every step must specify its output format explicitly. "Return a JSON array with this exact schema" is not over-specifying — it's necessary.

Mistake 3: Using the same model for every step

Your extraction and verification steps don't need GPT-4o or Claude Opus. A faster, cheaper model — Haiku, GPT-4o Mini, Llama 3.1 8B — can handle structured extraction reliably and at a fraction of the cost. Reserve expensive models for the synthesis step where reasoning quality matters. This alone can cut your chain's cost by 60–80%.

Mistake 4: Feeding too much context into later steps

Step 3 doesn't need to see the original source article. It only needs the verified claims from step 2. Trimming inputs to the minimum necessary data at each step improves accuracy and reduces token waste. Each step should receive a clean, purpose-built input — not the growing accumulated output of everything before it.

Mistake 5: No human checkpoints

Fully automated chains are powerful, but for high-stakes outputs, add at least one human review point. This is typically after verification — a human scans the verified claim set before the synthesis step runs. This is where you catch the extractions the model got subtly wrong, before they become the foundation of your final output.

Putting It All Together

Prompt chaining isn't a complex technique. It's a discipline: one step, one job. The payoff is disproportionate to the effort — chains that take 20 minutes to design routinely outperform hours of single-shot prompt engineering.

The pattern to internalise: whenever a task requires more than one cognitive mode (e.g., any combination of extraction, analysis, verification, and writing), it's a candidate for a chain. Whenever you're getting inconsistent results from a single-shot prompt, ask yourself which part of the task is being deprioritised — that's where you add a step.

Start with the three-step minimum: Extract → Verify → Synthesise. Master that pattern across a few different use cases. Then explore branching chains for comparative analysis, self-critique chains for high-quality writing, and fan-out chains for processing multiple sources in parallel.

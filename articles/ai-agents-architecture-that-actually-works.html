I Got Tired of AI Agents Breaking My Setup — Here's the Architecture That Actually Works

May 24, 2026 • 4 min read

The Root Cause of Most Agent Failures

Most agent failures fall into one of four categories: scope creep (the agent takes actions beyond what was intended), state confusion (the agent loses track of what's been done and what hasn't), error propagation (a wrong step early in a workflow contaminates every subsequent step), and permission overreach (the agent has access to things it shouldn't use and eventually does use them). Interestingly, none of these are model failures , they're architecture failures. Better models don't fix them. Better architecture does.

The Plan-First Pattern (Single Highest-use Change)

The most consistently reported improvement across every agent builder in the community: requiring the agent to produce a readable plan before executing any of it. Not for you , for itself. The agent writes out what it intends to do, in what order, and what the expected state of the world will be after each step.

One builder reported: "Adding a plan step cut my agent failure rate by 60%." The mechanism isn't mysterious. The plan step forces the LLM to surface its assumptions about the current state of the world, identify the inputs each step requires, and flag where it lacks information before it starts acting rather than halfway through. Errors that would have been discovered in step 4 are discovered in the plan. Discovering them in the plan is free. Discovering them in step 4 is expensive.

Implementation: before any multi-step agent execution, add a system prompt requirement: "Before taking any action, produce a numbered plan of what you intend to do, what you expect to find at each step, and what will constitute success. Submit the plan and wait for confirmation." The wait-for-confirmation step is optional , but the plan generation is not.

State Management: The Problem Nobody Talks About Enough

Stateless agents , agents that have no persistent memory of what they've done in previous runs , are the primary source of repetitive errors and unnecessary repeated actions. If your agent runs daily and doesn't know what it did yesterday, it will repeat yesterday's work, trigger duplicate notifications, and produce duplicate outputs. This is not a model problem. It's a state management problem.

Solutions that work in production:

  • Checkpoint files. After each significant action, the agent writes a structured record of what it did to a checkpoint file. On startup, the agent reads the checkpoint and picks up from where it left off. Simple, filesystem-based, and debuggable by humans.
  • Action logs with deduplication keys. Every agent action is logged with a unique key based on the action content. Before executing an action, the agent checks whether that key exists in the log. If it does, the action is skipped. This pattern is nearly immune to repetitive execution errors.
  • Separate "what to do" from "what has been done." Maintain two lists: the task queue (what the agent needs to do) and the completion log (what it has done). The agent works through the task queue and moves items to the completion log. Transparency is total , at any point you can see exactly where the agent is.

Error Recovery Architecture

The question to answer before deploying any agent: what happens when step 3 of a 7-step workflow fails? If the answer is "the whole workflow fails and I have to restart from step 1," your error recovery architecture is inadequate for production use. Proper error recovery has three components:

  1. Idempotent steps. Design each step so it can be run multiple times without causing harm. A step that "creates record if not exists" is idempotent. A step that "creates record" is not. Idempotency means you can safely retry failed steps without manual cleanup.
  2. Rollback definitions. For every step that creates, modifies, or deletes state, define what rollback looks like. This doesn't mean you always roll back , it means you can. Write the rollback logic at design time, when you're thinking clearly, not at 2am when the workflow is stuck in a bad state.
  3. Human escalation at defined failure thresholds. If a step fails three times in a row: stop, alert, wait. Don't let agents retry indefinitely. The threshold for human escalation should be defined in code, not discovered when the agent has sent 400 API requests trying to resolve something it cannot resolve autonomously.

Scope Discipline: The Ongoing Practice

Agent scope creep , the gradual expansion of what an agent does beyond what it was originally designed for , is the most common form of technical debt in agent systems. It happens because adding a new capability feels small in isolation and ends up large in aggregate. The agent that started as "summarize my emails" becomes "summarize my emails, flag action items, draft replies, schedule follow-ups, and occasionally book calendar events." Each addition seemed reasonable. The composite is an agent with an enormous blast radius and unclear responsibility boundaries.

The rule that prevents this: every capability addition requires a corresponding permission audit and a blast-radius reassessment. If the new capability increases what the agent can do to the world, the question is not "should we add this?" but "is our human oversight infrastructure adequate for the larger blast radius?"

For your current agent: does it produce a plan before acting, and can you read the complete state of what it has and hasn't done at any point? If not, those are the first two fixes , and they compound everything else you build on top of them.
